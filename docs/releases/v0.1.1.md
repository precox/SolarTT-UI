# SolarTT-UI v0.1.1 — stable release

The owner authorized **stable publication with documented limitations** on
12 November 2026. Publication is gated by exact-source tagged CI and verified
release assets. The tested basis is the public
**v0.1.1-alpha.1** package, source
`690b621074896cf6758f12ea5ff612f21197d82a`, package SHA256
`e2e54ee20fa441f50cfe94ff40ee094c9b5a47242ad3a6b1c0ac4356f948f6a4`.
The stable preparation changes version metadata and documentation only; runtime
logic, dependencies, configuration defaults, schema and managed patch are unchanged
from that tested basis. New version strings change binary digests, so this is
source-behavior equivalence, not a claim of identical ELF bytes. Existing release
tags and assets remain immutable.

See the [owner's stable decision](../stable-acceptance-2026-11-12.md),
[candidate evidence](../v0.1.1-candidate-acceptance-2026-11-12.md) and
[machine-readable acceptance](v0.1.1-acceptance.json). Publication does not
authorize a production installation.

## Fixes

- The managed endpoint rejects IPv4 multicast destinations. The previous adapter
  denied IPv6 and explicit own/blocked addresses but could admit locally scoped
  IPv4 multicast through upstream's destination filter. The fix is in SolarTT's
  adapter; the pinned managed upstream patch is unchanged.
- Monthly rollover processes all due users when one user cannot create a new
  quota period. Failed users retain their history and pending schedule; healthy
  users still receive their independent monthly transition. The call reports
  an error after the pass rather than silently hiding failed transitions.
- Listener regression evidence requires successful original TCP/UDP roundtrips,
  an elapsed listener deadline and a marked stream-loss assertion with fixture
  tasks still running. Unrelated setup or build failures do not prove the bug.
- The bundled SQLite is updated to 3.54.1 through Rusqlite 0.41.1 and
  libsqlite3-sys 0.39.1 for RUSTSEC-2026-0459. The backup call is adapted to the
  newer API; unsigned conversions and statement caching remain enabled. Exact
  archive and notice review covers the changed dependencies, including foldhash.

## Compatibility and verification scope

No database schema, configuration defaults, control API, device-profile format
or managed upstream patch changes. External dependencies change as described
above; the pinned Rust 1.95 toolchain satisfies their minimum versions. Normal IPv4
unicast forwarding and existing IPv6/private/own-address restrictions remain.
No production profiles or quota history need conversion.

Regressions cover multicast policy admission without multicast traffic,
continued UDP unicast and exact payload accounting, and A-at-period-cap/B-due
rollover across retries and restart. Disposable package upgrades cover published
v0.1.0 in addition to alpha.1, alpha.5 and alpha.6. The tested alpha passed its
[exact-tag CI](https://github.com/precox/SolarTT-UI/actions/runs/42709401124).
The stable candidate and eventual tag must pass their own full workflow; alpha
results do not attest binaries built with the new stable version.

## Completed candidate acceptance

- Official TrustTunnel Android 1.2.0 on Android 17: owner confirmed normal Wi-Fi
  access and automatic Wi-Fi/mobile/Wi-Fi recovery, quota policy restoration and
  denial of a revoked profile on manual reconnect.
- Quota and revocation for synthetic A preserved B's original verified TCP/DoT
  and UDP/DNS streams: 358 successful paired exchanges over 1,796.503 seconds,
  without reconnects. Manual quota testing lowered the limit below existing
  spend; natural traffic exhaustion remains separately covered by CI.
- Matching-key local QA database backup/restore passed. Stale rollback was
  refused; the saved B profile worked after restore and revoked A stayed denied.
- The owner explicitly shortened the planned 24-hour observation and accepted
  **20 h 39 min**: 1,240 samples, 248 periodic public TCP/UDP probes plus a final
  probe, zero health/collection/probe failures, restarts or OOM events. This was
  a loopback-only shared-host process cohost under light synthetic load.
- Real staging DNS-01 issuance and Certbot `renew --dry-run --run-deploy-hooks`
  passed. The isolated QA agent acknowledged TLS reload without restarting;
  original TCP/UDP streams survived and a fresh verified TLS/H2 connection passed.
- Temporary QA processes, state, keys/profiles, accounts and test DNS records
  were removed; production identities and selected configuration were unchanged.

## Remaining verification limits

The supported target remains Ubuntu 24.04 x86_64 with systemd. Network reachability,
capacity benchmarks, independent full-stack recovery and actual public-certificate
replacement retain the explicit verification limits. There is no advertised
concurrent-client count, throughput/UDP-loss envelope or censorship-resistance
guarantee. The shortened observation is not a completed 24-hour or capacity test.
Local database restore is not recovery of a complete lost host. Owner-mediated
staging DNS hooks do not establish unattended production DNS automation; dry-run
deploy hooks use the active staging leaf, not a newly installed public certificate.
Manual panel UI was not repeated because its implementation is unchanged;
portable/browser CI remains separately required. A natural calendar rollover
was not manually observed; timestamp-injected regression coverage remains separate.

The exact stable tag must pass all nine
required CI jobs across the six prerequisite gate families before the publisher
can attach reports and expose the release. Public packages and checksums then
require independent download verification. Installation on an existing node
requires its own operational window, consistent backup and recovery plan.

The fresh source audit also reports informational RustSec `unsound` warnings for
Rustix 1.1.5 and Tokio 1.53.2, in addition to the existing unmaintained
`rustls-pemfile` warnings. The
[dated applicability review](../dependency-advisory-review-2026-11-12.md) found
no affected execution path in the supported managed mode: the agent rejects
ICMP/ping before core construction, and tempfile does not use the affected xattr
functions. This is scoped source/binary evidence, not a universal safety claim.
Warnings remain visible; Tokio 1.53.3 and Rustix 1.1.6 are separate maintenance
candidates. This version/documentation-only PR does not change dependencies.
